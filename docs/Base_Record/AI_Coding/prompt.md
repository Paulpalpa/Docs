# Prompt（编码场景）

Prompt 就是这轮给模型的明确指令。写得好不好，不在文采，在于目标、约束、要它看什么、输出成什么样、怎样算做完，有没有说清楚。

## 一、核心概念

### 1.1 Prompt 能管什么，管不了什么

| 写清楚 Prompt 往往有用 | 单靠 Prompt 很难解决 |
| --- | --- |
| 目标歧义、输出形态乱 | 关键文件根本没进上下文 |
| 乱改范围、顺手重构 | 没有测试 / 类型检查反馈 |
| 「先分析再改」 | 权限过大导致的误操作 |
| 做到哪停、何时要问人 | Spec 本身写错或过期 |

Prompt 重要，但 Context、Harness、Spec 替不了。

### 1.2 和 Context 怎么分工

| | Prompt | Context |
| --- | --- | --- |
| 是什么 | 要它做什么 | 做事时能用到的信息和长期约定 |
| 常见载体 | 对话、任务描述 | 打开的文件、Rules、@ 引用、搜索结果、工具输出 |
| 怎么改更好 | 说清楚、能执行、能验收、能停 | 够用就行、相关、别过期 |

相关文件都不在场时，再打磨措辞收益也有限。先把该看的东西给到，再磨句子。

### 1.3 写 Prompt 时可以按这几块想

1. 目标：干什么（对象 + 结果）  
2. 非目标 / 约束：别做什么、必须跟什么  
3. 上下文：先看哪些模块；不知道就怎么搜  
4. 做法：先计划 / 先复现 / 最小改动 / 照着哪个文件写  
5. 输出：只分析、改代码、还是按条目审  
6. 验收和停止：怎样算完；什么情况必须先问人  

「别做什么」和「什么时候停」经常被漏掉，一漏就容易越改越多，或者死循环修同一个错。

### 1.4 少堆形容词，多写能对照的约束

模型对「优雅、健壮、生产级」这类词其实不太敏感，对能对照的约束更敏感。

弱：

```text
请写出优雅、健壮、生产级、高性能的代码
```

强：

```text
错误处理跟 src/services/user.ts 一样；
不要引入新依赖；
公共函数签名别改；
补 401 / 超时的失败用例；
改动就卡在这两个文件里
```

「优雅」没法验收；「跟某个文件一样」可以对着看。

## 二、怎么做

### 2.1 比较管用的几招

1. 先让它复述目标和约束，有歧义先问。  
2. 每次写几条「这次不做」。  
3. 点名「照着哪个现有文件写」。  
4. 分阶段：先只读分析，确认前别改文件。  
5. 要求最小 diff，禁止无关格式化。  
6. 修 bug 先复现或贴失败日志，再改。  
7. 规定回复结构，少听空话。  
8. 同一失败连续两次还没新证据 → 停下说明假设和缺什么。

### 2.2 场景模板

#### 修 Bug

```text
现象：实际 <A>，期望 <B>
复现：<步骤 / 环境 / 版本>
证据：<报错栈 / 失败测试名>
相关位置：<已知路径；不知道就先搜再报告>
阶段：
  1) 只读定位根因（文件 + 理由）
  2) 我确认后再最小改动修复
  3) 补或更新测试
不要：无关重构；改公共 API（除非必要并先说明）
验收：复现消失；命令：<test/lint>
停止：复现不了就列缺什么，别猜着改
```

#### 加功能

```text
需求：<一句话说清谁在什么场景要什么>
范围：<页面 / API / 模块>
非目标：<例如不做国际化、不做权限重构>
参考实现：<路径>
顺序：先主路径 + 测试，再边界和错误态
每片结束：列改了哪些文件、验收结果
验收：<行为或用例>
约束：不改后端契约；不新增依赖
```

#### 重构

```text
主目标：只做 <可读性|去重|解耦|性能> 里的一个
范围：仅 <路径>
不变：对外行为和公共 API；现有测试要继续过
步骤：先给计划、风险、怎么回滚 → 确认后再小步改
禁止：借重构改行为；扩到范围外
验收：<test 命令> 通过；行为没有差
```

#### 写测试

```text
被测：<文件/函数>
风格：先看邻近测试，跟仓库现有框架和目录
覆盖：主路径 + 列出的边界
测行为和契约，别死磕私有实现细节
不要：为了覆盖率改生产代码；疑似 bug 先报告
验收：测试能单独跑过；命名跟旁边一致
```

#### Code Review

```text
范围：<PR / diff / 文件列表>
优先看：正确性 > 安全 > 回归 > 性能 > 可维护性 > 风格
输出：
  - [严重] path: 问题 / 原因 / 建议
  - [中等] ...
  - [建议] ...
每条要能定位；没依据别写；别抬杠纯风格偏好
另外列出需要作者确认的假设
```

#### 排查性能

```text
症状：<慢在哪 / 指标 / 环境>
已有线索：<profile / 日志 / 怀疑点>
先给测量计划和假设，再改代码
不要：没量就大规模重写
验收：说明怎么对比改前后；回归测试过
```

### 2.3 差和好比一比

差：

```text
帮我优化一下这个项目，弄好一点，顺便看看有没有安全问题。
```

目标没法验、范围没边、好几件事捆一起。

好：

```text
目标：UserList 首屏改成服务端分页，默认 pageSize=20。
非目标：不做虚拟滚动；不改排序；不动权限。
范围：src/pages/UserList/** 和对应 API hook；别动后端。
参考：src/pages/OrderList 的分页。
阶段：先对比 OrderList 出改动计划，确认后再改。
验收：
  1) 首屏网络请求只有一页；
  2) 翻页 page 递增；
  3) yarn test UserList 通过。
停止：后端 page 参数和假设不符时，先报告实际契约。
```

### 2.4 Rules 里适合长期放什么

适合：

- 语言、回复习惯  
- 仓库硬约束（包管理器、测试命令、禁止 force push）  
- 安全红线  

不适合：

- 某个临时 bug 的细节  
- 一堆互相打架的「永远 / 绝不」  
- 过期的架构宣言  

更细的分层见 [Context 工程](./context-engineering.md)。

### 2.5 多轮对话里注意

- 一轮尽量只推一个主目标，旁支出去开新任务。  
- 纠正时把正确事实再说一遍，只回「不对」的话，旧错误还在上下文里。  
- 告一段落后可以写一小段摘要：目标、已定决策、未决问题、当前文件。  
- 已经聊脏了就重开，把摘要贴过去，通常比在旧线程里抢救省事。

## 三、常见坑

- 形容词堆很多，却没有一条能验收的约束。  
- 修 bug、重构、换技术栈捆在一句话里，失败了也不知道怪谁。  
- 不写「不做」，模型常会「好心」扩大范围。  
- 你要方案，它直接改仓库（或反过来）。  
- 把很长的旧对话当成仍然有效的 Prompt。  
- 「你是世界顶级专家」这类角色扮演，基本没有工程收益。  
- 验收只在自己心里，从没写出来。  
- 复制网上很长的通用模板，和本仓库无关，变成噪声。
