# AI Coding Flow

Flow 讲的是：人和 Agent 这一轮（或多轮）怎么协作。Prompt 写得好，只能提高单步命中率；整条链路能不能控住、能不能审、能不能停，靠的是工作方式。

## 一、核心概念

### 1.1 没有明确流程时，会话经常长这样

```text
需求一句 → Agent 大改 → 说不对 → 再改 → 还不对 → 上下文炸了 → 重开或放弃
```

把流程说清楚，是为了把不确定的事先谈开，把验证嵌进循环，而不是靠下一轮聊天把上一轮失败糊过去。

### 1.2 五个阶段

```mermaid
flowchart LR
  Understand[理解需求] --> Plan[规划]
  Plan --> Implement[实现]
  Implement --> Verify[验证]
  Verify --> Iterate[迭代]
  Iterate --> Understand
```

| 阶段 | 人 | AI | 这阶段结束时手上该有什么 |
| --- | --- | --- | --- |
| 理解 | 澄清目标、约束、不做的事 | 提问、复述、标歧义 | 对齐过的任务描述 |
| 规划 | 拍板方案和范围 | 拆任务、列文件、标风险 | 计划 / 影响面 |
| 实现 | 盯关键决策、卡住越界 | 读代码、改文件、写测试 | 能审的 diff |
| 验证 | 确认怎么算过 | 跑命令、对照用例 | 通过或失败的证据 |
| 迭代 | 决定继续、回滚、收窄或改 Spec | 按证据改 | 下一片要做什么 |

心里有方案 ≠ 规划完了；感觉测过了 ≠ 验证完了。

### 1.3 模式怎么选：看你清楚多少，别看习惯

以 Cursor 一类工具为例（名字因产品而异）：

| 模式 | 适合 | 不适合 |
| --- | --- | --- |
| Ask / 只读 | 还不懂现状、要比方案、先排思路 | 改点已经定了，就差落地 |
| Plan | 需求糊、改动面大、有架构取舍 | 一行已知修复 |
| Agent | 目标清、有验收、范围可控 | 目标糊、没边界、没法验证 |

可以粗暴地想：

```text
「改哪里 / 改成什么样 / 怎么验收」这三样
清楚 0～1 个 → 先 Ask，或先把 Spec 补上
清楚 2 个 → Plan
三个都清楚 → Agent
```

越不确定，越先 Ask / Plan；越确定，再上 Agent。

### 1.4 哪些决定该人拍板

| 类型 | 谁主 | 例子 |
| --- | --- | --- |
| 价值、优先级 | 人 | 先做 A 还是 B；要不要兼容旧接口 |
| 安全、合规 | 人 | 能不能碰生产数据；能不能推远程 |
| 已知约束里的选型 | 可以一起聊，人定 | 仓库已有惯例就跟惯例 |
| 搜索、起草、跑检查 | AI | 找引用、改样板、跑测试 |
| 算不算完成 | 人看验收 + AI 给命令输出 | — |

AI 擅长降搜索和起草成本；不可逆后果和业务取舍，别甩给它独自扛。

### 1.5 大任务怎么拆

| 拆法 | 做法 | 好处 | 问题 |
| --- | --- | --- | --- |
| 按一条用户路径切 | 每次做出一条能验收的路径 | 每步能验证、能演示 | 早期抽象可能来回改 |
| 按层切 | 先 API 全做完，再 UI，再测试 | 看起来整齐 | 很晚才有整体可验证；中间难停 |

更推荐按路径切：每片都走完「实现 → 验证」，再进下一片。最怕改了很久，却还证明不了任何一条路径是对的。

## 二、怎么做

### 2.1 开场可以这么写

```text
目标：<一句话，对象 + 结果>
非目标：<这次明确不做>
范围：只改 <路径/模块>；不要动 <列表>
背景：<现象 / issue / 复现>
参考：<可以照着写的现有实现>
验收：
  1) <命令>
  2) <点一下能看出来的行为>
约束：跟现有风格；不新增依赖（除非先说理由）
卡住时：先说缺什么信息、你做了什么假设，别猜着大改
```

### 2.2 动手前先要一份影响面

进入改代码前，可以让它按这个结构回：

```text
1. 复述问题（标出理解里的歧义）
2. 相关文件（路径 + 为什么相关）
3. 方案（最好不超过两个）和取舍
4. 建议的改动顺序
5. 风险和回归点
6. 需要你确认的问题（尽量能用是/否答）
```

人主要答第 6 点里关键的，然后定方案。

### 2.3 控制单次改动体积

| 单次会话大概 | 建议 |
| --- | --- |
| 三五个文件以内，净变更不太夸张 | 一般还能审 |
| 更大 | 拆片，或先 Plan；明确「只做第 N 片」 |
| 出现大片格式化/重排 | 叫停，让还原无关改动 |

Prompt 里可以直接写死：

```text
本轮只做切片 1：……
切片外的文件先别动。如果发现必须动，先停下说明原因。
```

### 2.4 验证可以按力度加

| 力度 | 手段 | 什么时候 |
| --- | --- | --- |
| 烟测 | 启动、点一条主路径 | UI / 集成改动至少做这个 |
| 静态 | typecheck / lint | 提交前基本都该有 |
| 单测 | 相关或新增单测 | 逻辑变了 |
| 契约 | API fixture / contract | 接口变了 |
| 对照 Spec | 逐条勾 | 有写 Spec 时 |

验收命令写进任务里，后面接测试反馈会顺很多。

### 2.5 失败了别只会「再试试」

1. 先看证据：日志、失败断言、实际 diff  
2. 分一下是哪类：理解错 / 范围扩了 / 实现 bug / 环境问题 / Spec 本身不对  
3. 再动手：  
   - 理解错 → 回到理解，重说目标  
   - 范围扩了 → 回滚越界，收紧允许改的路径  
   - 实现 bug → 小范围修，别顺手重构  
   - Spec 错 → 先改 Spec，再改代码  
4. 线程已经脏了就新开：带上已确认事实、当前 diff 摘要、失败证据  

### 2.6 小例子：用户列表加分页

1. 理解：pageSize、要不要动后端、旧的一次拉全量还要不要兼容。  
2. 规划：影响 `UserList`、请求 hook、mock；选定「后端已有 page 参数，前端按页请求」。  
3. 切片 1：只改 hook 和请求参数，测试证明带了 `page/pageSize`。  
4. 切片 2：Table 接分页，手点翻页。  
5. 切片 3：空态、错误态。  
6. 收尾：看一眼有没有无关文件被改到。  

第一步后端契约都不清，就先别让 Agent「先写着」。

## 三、常见坑

- 聊了很久，却从没写出怎样算完成。  
- 需求还糊就直接 Agent，后面返工往往比多花几分钟规划更贵。  
- 按层大拆、很晚才合并：失败难定位。  
- 同一个错假设在长对话里反复被强化。  
- 把「Agent 说测过了」当成验收。  
- 只验快乐路径：权限、空数据、失败重试上线才爆。  
- 多个 Agent 同时改同一目录，没有协调，互相覆盖。
