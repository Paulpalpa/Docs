# Spec Driven Development

Spec Driven 的意思很简单：先把「怎样算对」写成能验收的规格，再让 AI 按这个实现。聊天里的模糊意图，不够当协作锚点；能勾选的约定，才方便人和 Agent 对齐，也方便事后回归。

## 一、核心概念

### 1.1 Spec 是什么，不是什么

是：能回答「做成什么样算对 / 什么情况算错」的东西。  
不是：越长越好的愿景文，也不是没人维护的过期 wiki。

常见形态（可以组合）：

| 形态 | 内容 | 好不好验收 |
| --- | --- | --- |
| 需求说明 | 目标、非目标、范围 | 中（得把验收写清） |
| 行为用例 | Given / When / Then | 高 |
| 接口契约 | 字段、错误码、兼容策略 | 高 |
| 状态 / 时序 | 合法迁移、非法迁移 | 高 |
| 架构约束 | 分层、依赖方向、禁止事项 | 中到高 |
| 可执行测试 | 单测 / 契约测 / e2e | 最高 |

关键是能不能验证，不是有没有文档。

### 1.2 为什么跟 AI 协作时更需要

人对人开发，口头需求和会上补一句还能凑合；人对 Agent：

- 它不会开完会突然懂业务  
- 长对话里的隐含约定很容易丢或拧  
- 没有写清的成功标准时，它容易往「看起来像做完」优化  

Spec 主要用来：对齐目标、缩小乱改空间、提供验收、跨会话把决策留下来。

### 1.3 闭环

```mermaid
flowchart LR
  Intent[意图] --> Draft[起草]
  Draft --> Align[对照仓库校准]
  Align --> Freeze[定稿]
  Freeze --> Implement[实现]
  Implement --> Check[对照验收]
  Check -->|失败且规格对| Implement
  Check -->|失败且规格错| Draft
  Check -->|通过| Sync[同步规格和代码]
```

和 TDD / 契约测试的关系：测试是 Spec 的一种强形式；不是每个任务都要先写红灯测试，但非琐碎任务总该有某种能说清的成功标准。

### 1.4 写多细合适

| 强度 | 形态 | 适合 |
| --- | --- | --- |
| 轻 | 验收条目 + 非目标 + 范围 | 中小功能、单模块 |
| 中 | 再加上接口字段、错误码、兼容 | API、跨端约定 |
| 强 | 再加上可执行测试 / 状态机等 | 核心链路、回归贵、多人协作 |

失败代价高、参与人多、跨模块 → 往上加。  
已经精确到改哪几行 → 写一句验收就够，别为形式硬写长篇。

## 二、怎么做

### 2.1 轻量模板

```markdown
# <功能名> Spec

## 1. 背景与目标
- 要解决的问题：
- 成功时能观察到：

## 2. 非目标
- 这次明确不做：

## 3. 范围
- 涉及模块/路径：
- 明确不改：

## 4. 行为与验收
1. Given ... When ... Then ...
2. Given ... When ... Then ...
3. 失败态：Given ... When ... Then ...

## 5. 约束
- 兼容性：
- 性能/安全（如有）：
- 技术约束（依赖、模式、参考实现）：

## 6. 开放问题
- 实现前必须确认：

## 7. 验收命令
- 命令：
```

### 2.2 接口段落示例

```markdown
## API: GET /api/users
Query:
  - page: int >= 1，默认 1
  - pageSize: int，默认 20，最大 100
Response 200:
  - items: User[]
  - total: number
Error:
  - 400 invalid_query：参数不合法
兼容：
  - 不删既有字段；新字段必须可选
```

把这段同时给实现和测试（或同一 Agent 的测试那片），比口头「做个分页」稳得多。

### 2.3 和 AI 一起走的节奏

1. 人写要点，或让 AI 起草 → **人必须过一遍**。  
2. 只读对照仓库，标出和现状冲突、缺了哪些假设。  
3. 开放问题清掉，或明确写「实现时不许擅自定」。  
4. 实现：按定稿来；对不上先停。  
5. 验收逐条勾；失败先分清是代码错还是 Spec 错。  
6. 合入时同步 Spec / 文档 / 测试，避免两套各说各话。  

第 5 步很关键：很多人失败后只改代码，错误 Spec 被绕过去，下一轮又被旧 Spec 带偏。

### 2.4 让 AI 起草时可以这样说

```text
根据下面意图起草轻量 Spec（用既定模板）。
要求：
- 每条验收必须能客观判断过/不过；
- 写清非目标；
- 标出你做的假设；
- 标出需要我确认的开放问题（尽量是/否能答）；
- 先别写业务代码。
意图：<...>
已知约束：<...>
```

### 2.5 验收时怎么处理结果

| 结果 | 动作 |
| --- | --- |
| 代码不满足正确 Spec | 改代码，Spec 不动 |
| Spec 和真实产品决策冲突 | 先改 Spec，再改代码 |
| 验收条目本身没法判定 | 先改 Spec 表述 |
| 做了写在非目标里的事 | 回滚越界，非目标写得更死一点 |

### 2.6 小例子：用户列表分页

定稿后的验收可以长这样：

1. 后端已支持 page/pageSize 时，打开 UserList，首屏只请求 page=1&pageSize=20。  
2. 点第 2 页，请求 page=2，表格数据对得上。  
3. 后端 500 时，走现有错误态，不白屏。  
4. 不做无限滚动，不改排序。  
5. `yarn test UserList` 通过。  

如果 Agent 开始做虚拟列表，那是越界，不是「增强」。

### 2.7 放哪、怎么维护

- 和功能同目录的 `SPEC.md`、`docs/specs/xxx.md`、Issue 正文都行；要紧的是实现时找得到，改完会更新。  
- 短命实验可以用 PR 描述顶一阵；功能留下来了，就挪到更好找的地方。  
- 过期的要么更新，要么标废弃，别继续喂进上下文。  

## 三、常见坑

- 背景写很长，没有一条能勾的验收。  
- 代码变了 Spec 不变，Agent 按旧约干活。  
- 改文案也写长篇，成本倒挂。  
- AI 起草的 Spec 没人审就开写，错误假设被放大。  
- 只验快乐路径：权限、空数据、超时、并发都没写。  
- 把设计幻灯片当成 Spec。  
- 开放问题实现时私下拍板，事后扯皮。  
- 测试很多但没盖住真正契约，看着安心其实虚。
